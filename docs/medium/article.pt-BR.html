Consultando CEPs com Flutter

Notas de aula do prof. Kleber de Oliveira Andrade

Como transformar oito números em um endereço legível? Nesta aula vamos consultar o ViaCEP com Flutter, validar a entrada antes de acessar a rede e apresentar o resultado em uma interface acessível. O objetivo é compreender cada responsabilidade, do campo de texto até a resposta HTTP, e aprender a lidar com os caminhos em que a consulta falha.

O CEP — Código de Endereçamento Postal — tem oito algarismos. Ele pode identificar um logradouro, uma localidade ou uma unidade específica. Por isso, um retorno sem rua ou bairro não significa necessariamente um erro. Os zeros à esquerda também fazem parte do código: CEP é texto, não um número para fazer contas.

Atualização da aula, novembro de 2026: o aplicativo está na versão 2.0.1+3 e usa Flutter 3.50.0, Dart 3.14.0, null safety e Material 3. Os dois overrides descritos nesta aula foram adotados somente após testes e builds nesta combinação de versões. O título, a autoria e a finalidade desta nota de aula de 2019 foram mantidos. Os exemplos abaixo acompanham o código atual do repositório; os antigos componentes e capturas foram substituídos.

O que você vai aprender

  • Validar e normalizar um CEP sem perder zeros à esquerda.
  • Fazer uma requisição HTTPS com um cliente HTTP que pode ser substituído nos testes.
  • Converter JSON em um endereço imutável e validar dados externos.
  • Distinguir carregamento, sucesso, entrada inválida, CEP inexistente e falha de conexão.
  • Impedir que uma resposta atrasada substitua uma pesquisa mais recente.
  • Testar a lógica e a interface usando exemplos controlados.

Por que existem dois overrides?

Ao migrar do SDK anterior para Flutter 3.50.0, oito dos nove pacotes transitivos avançaram de versão. Ainda havia duas restrições exatas no próprio SDK: material_color_utilities: 0.13.0 e test_api: 0.7.14. As versões mais recentes são, respectivamente, 0.13.1 e 0.7.15. Nesta versão do aplicativo, adotamos overrides exatos para essas duas versões após verificar a compatibilidade local e no CI.

dependency_overrides tem precedência sobre as restrições normais, inclusive as declaradas por dependências do SDK. Ele faz o Pub escolher a versão indicada; não demonstra, sozinho, que a troca é compatível. Por isso, o experimento foi primeiro colocado em pubspec_overrides.yaml, um arquivo local temporário. Depois de análise, 21 testes e builds Web, macOS release e iOS sem assinatura passarem, os overrides foram promovidos para o pubspec.yaml compartilhado.

Os dois pacotes afetam partes diferentes do projeto. material_color_utilities participa do cálculo das cores Material; sua atualização exige verificar o tema e a apresentação real do app. test_api participa da infraestrutura dos testes, então a suíte precisa continuar descobrindo, executando e avaliando corretamente seus cenários. Testar somente se as dependências foram baixadas não cobre esses comportamentos.

Com os overrides ativos, os nove pacotes antes apontados estão nas versões mais recentes verificadas nesta aula. 3. API, HTTPS e JSON: o caminho da consulta

Uma API é uma interface pela qual programas trocam informações. Aqui o aplicativo envia uma requisição GET ao ViaCEP e recebe um documento JSON. JSON é o formato dos dados; o endereço na tela é a interpretação desses dados pelo nosso código.

https://viacep.com.br/ws/01001000/json/

Observe que a URL usa somente os oito dígitos. O exemplo desta aula corresponde ao CEP 01001-000, em São Paulo. No artigo antigo o rótulo do link e o CEP do destino não coincidiam; agora usamos um único exemplo coerente.

{"cep":"01001-000","logradouro":"Praça da Sé","complemento":"lado ímpar","bairro":"Sé","localidade":"São Paulo","uf":"SP","unidade":"","ibge":"3550308","gia":"1004","ddd":"11","siafi":"7107"}

Campos como complemento, bairro ou logradouro podem estar vazios em outras respostas. Um CEP bem formado também pode não existir: nesse caso o serviço pode responder com HTTP 200 e {"erro": true}. Portanto, precisamos verificar tanto o status HTTP quanto o conteúdo recebido. Não confunda “requisição atendida” com “endereço encontrado”.

4. Valide na entrada: a classe Cep

A regra fica em um único lugar, lib/domain/cep.dart. Cep.parse aceita oito dígitos ou a máscara 00000-000 e remove espaços apenas nas extremidades. Letras, pontuação inesperada e comprimentos incorretos geram FormatException antes de qualquer chamada à rede.

/// Brazilian postal code: eight ASCII digits; leading zeros are significant.
final class Cep {
  const Cep._(this.digits);
  final String digits;
  factory Cep.parse(String input) {
    final value = input.trim();
    if (!RegExp(r'^[0-9]{5}-?[0-9]{3}$').hasMatch(value)) {
      throw const FormatException('Informe um CEP com 8 dígitos.');
    }
    return Cep._(value.replaceAll('-', ''));
  }
  String get formatted => '${digits.substring(0, 5)}-${digits.substring(5)}';
}

Experimente: 01001000 e 01001-000 devem representar o mesmo CEP. Já “123”, “a01001000” e “0100-1000” devem ser rejeitados. A expressão regular verifica o formato, não a existência do endereço — essa segunda verificação pertence ao serviço.

5. Modele o endereço e confira o retorno

A classe ResultCep representa a resposta em memória. Seus dados são imutáveis: depois da criação, a tela não pode alterar acidentalmente o endereço. fromMap confere os tipos dos campos, valida o CEP retornado e exige cidade e UF coerentes. Campos opcionais ausentes recebem texto vazio.

Trecho do modelo: o retorno válido é armazenado em um mapa não modificável. Os getters expõem os campos usados na tela, enquanto toMap devolve uma cópia e toJson permite inspecionar a serialização. Consulte o arquivo completo para acompanhar os demais campos, incluindo os já presentes na versão original da aula.

  factory ResultCep.fromMap(Map<String, dynamic> map) {
    final fields = <String, String>{};
    for (final key in [
      'cep',
      'logradouro',
      'complemento',
      'bairro',
      'localidade',
      'uf',
      'unidade',
      'ibge',
      'gia',
      'ddd',
      'siafi',
      'estado',
      'regiao',
    ]) {
      final value = map[key];
      if (value != null && value is! String) {
        throw FormatException('Invalid $key');
      }
      fields[key] = (value as String? ?? '').trim();
    }
    fields['cep'] = Cep.parse(fields['cep']!).formatted;
    if (fields['localidade']!.isEmpty ||
        !RegExp(r'^[A-Z]{2}$').hasMatch(fields['uf']!)) {
      throw const FormatException('Missing city or state');
    }
    return ResultCep._(Map.unmodifiable(fields));
  }

Não há persistência neste aplicativo. Converter JSON em objeto não significa gravar um banco de dados ou histórico. Se você acrescentar armazenamento como exercício, precisará decidir como limpar, proteger e migrar os dados.

6. Isole a rede: ViaCepService

O serviço recebe um http.Client pelo construtor. Em produção usamos o cliente real; nos testes usamos MockClient. Assim podemos testar respostas inválidas e timeout sem depender da disponibilidade da internet. Quem cria o cliente também deve fechá-lo quando terminar de usá-lo.

A interface AddressLookup define uma única operação: receber um CEP validado e devolver um endereço. A implementação real usa Uri.https, decodificação UTF-8 e timeout de dez segundos. Veja o serviço completo:

import 'dart:async';
import 'dart:convert';
import 'package:http/http.dart' as http;
import '../domain/cep.dart';
import '../models/result_cep.dart';
enum FailureKind { notFound, unavailable, invalidResponse, timeout, network }
final class LookupFailure implements Exception {
  const LookupFailure(this.kind);
  final FailureKind kind;
  String get message => switch (kind) {
    FailureKind.notFound =>
      'CEP não encontrado. Confira os números e tente outro CEP.',
    FailureKind.unavailable =>
      'O ViaCEP está indisponível. Tente novamente em instantes.',
    FailureKind.invalidResponse =>
      'O serviço retornou uma resposta inválida. Tente novamente.',
    FailureKind.timeout => 'A consulta demorou demais. Tente novamente.',
    FailureKind.network =>
      'Não foi possível conectar. Verifique sua conexão e tente novamente.',
  };
}
abstract interface class AddressLookup {
  Future<ResultCep> lookup(Cep cep);
}
class ViaCepService implements AddressLookup {
  ViaCepService(this.client, {this.timeout = const Duration(seconds: 10)});
  final http.Client client;
  final Duration timeout;
  @override
  Future<ResultCep> lookup(Cep cep) async {
    try {
      final response = await client
          .get(Uri.https('viacep.com.br', '/ws/${cep.digits}/json/'))
          .timeout(timeout);
      if (response.statusCode != 200) {
        throw const LookupFailure(FailureKind.unavailable);
      }
      return _decode(utf8.decode(response.bodyBytes), cep);
    } on TimeoutException {
      throw const LookupFailure(FailureKind.timeout);
    } on http.ClientException {
      throw const LookupFailure(FailureKind.network);
    } on FormatException {
      throw const LookupFailure(FailureKind.invalidResponse);
    }
  }
  ResultCep _decode(String body, Cep requested) {
    final decoded = jsonDecode(body);
    if (decoded is! Map<String, dynamic>) {
      throw const FormatException('Expected object');
    }
    if (decoded['erro'] == true || decoded['erro'] == 'true') {
      throw const LookupFailure(FailureKind.notFound);
    }
    final address = ResultCep.fromMap(decoded);
    if (address.cep != requested.formatted) {
      throw const FormatException('Unexpected CEP');
    }
    return address;
  }
}

Leia o método em três passos: primeiro obtenha a resposta; depois confira o status e decodifique o corpo; por último valide o objeto e compare o CEP recebido com o solicitado. LookupFailure mantém categorias diferentes de falha, permitindo mensagens úteis para a pessoa que faz a consulta.

Checkpoint: uma resposta com erro deve virar “CEP não encontrado”; uma falha de rede deve pedir para verificar a conexão; JSON inválido deve informar que a resposta do serviço não pôde ser usada. O aplicativo não deve encerrar com uma exceção sem tratamento.

7. Controle os estados e as respostas atrasadas

A tela precisa representar quatro situações: inicial, carregando, sucesso e erro. Elas são classes de um tipo sealed, em SearchController. Isso permite usar um switch que cobre todos os estados.

Imagine duas consultas: a primeira demora, mas a segunda responde rapidamente. Sem controle, a primeira resposta poderia sobrescrever a segunda. Cada busca ou edição incrementa uma geração; o resultado só é aplicado se ainda pertence à geração mais recente. As requisições antigas podem terminar em segundo plano, mas seus resultados são ignorados.

import 'package:flutter/foundation.dart';
import '../domain/cep.dart';
import '../models/result_cep.dart';
import '../services/via_cep_service.dart';
sealed class SearchState {
  const SearchState();
}
final class SearchIdle extends SearchState {
  const SearchIdle();
}
final class SearchLoading extends SearchState {
  const SearchLoading();
}
final class SearchSuccess extends SearchState {
  const SearchSuccess(this.address);
  final ResultCep address;
}
final class SearchError extends SearchState {
  const SearchError(this.message);
  final String message;
}
/// Each edit/search invalidates older responses without blocking the input.
class SearchController extends ChangeNotifier {
  SearchController(this.service);
  final AddressLookup service;
  SearchState state = const SearchIdle();
  int _generation = 0;
  bool _disposed = false;
  void inputChanged() {
    _generation++;
    _emit(const SearchIdle());
  }
  Future<void> search(String input) async {
    final generation = ++_generation;
    try {
      final cep = Cep.parse(input);
      _emit(const SearchLoading());
      final address = await service.lookup(cep);
      if (generation == _generation) _emit(SearchSuccess(address));
    } on FormatException {
      if (generation == _generation) {
        _emit(
          const SearchError(
            'Informe um CEP com 8 dígitos. Exemplo: 01001-000.',
          ),
        );
      }
    } on LookupFailure catch (error) {
      if (generation == _generation) _emit(SearchError(error.message));
    }
  }
  void _emit(SearchState next) {
    if (_disposed) return;
    state = next;
    notifyListeners();
  }
  @override
  void dispose() {
    _disposed = true;
    _generation++;
    super.dispose();
  }
}

Observe a sequência em search: validar, emitir carregamento, esperar o serviço e publicar o resultado se a geração ainda for atual. inputChanged invalida a consulta anterior, e dispose impede notificações depois que o controlador foi encerrado.

8. Apresente informações em vez de JSON bruto

Em main.dart, CepApp configura Material 3 e a localização em português usando o pacote independente material_ui. O widget proprietário cria o cliente e o controlador quando eles não são injetados e libera esses recursos no descarte. A HomePage completa separa formulário, painel de status e cartão de endereço em widgets.

O campo usa TextInputAction.search: pressionar Enter realiza a busca. O botão Limpar CEP apaga entrada e resultado e devolve o foco ao campo. O texto permanece editável durante a consulta, e os estados de carregamento e erro não bloqueiam uma nova tentativa.

Este trecho real de HomePage escolhe a apresentação de cada estado:

  Widget _result(search.SearchState state) => switch (state) {
    search.SearchSuccess(:final address) => _AddressPanel(address: address),
    search.SearchLoading() => const _StatusPanel(
      icon: Icons.travel_explore,
      title: 'Consultando o ViaCEP…',
      message: 'Você pode alterar o CEP enquanto espera.',
      loading: true,
    ),
    search.SearchError(:final message) => _StatusPanel(
      icon: Icons.info_outline,
      title: 'Vamos tentar de novo?',
      message: message,
      error: true,
    ),
    search.SearchIdle() => const _StatusPanel(
      icon: Icons.location_on_outlined,
      title: 'Seu próximo destino começa aqui',
      message: 'O endereço aparecerá aqui após a consulta.\nSe preferir, comece por um dos exemplos.',
    ),
  };

O retorno é exibido em campos selecionáveis: CEP, logradouro, bairro, cidade/UF, complemento, DDD e IBGE, conforme o que o serviço informar. Os valores também possuem rótulos acessíveis, e as mudanças de estado são anunciadas pela semântica do Flutter. O botão Copiar endereço mostra uma confirmação; se a área de transferência falhar, o texto continua disponível para seleção.

Em telas largas os painéis ficam lado a lado. Em telas estreitas passam para uma coluna com rolagem. Não use largura fixa para todo o conteúdo: o mesmo formulário precisa funcionar quando a pessoa amplia a fonte ou utiliza uma tela menor.

5 desafios de melhoria para desenvolver

  1. Alternância de temas. Adicione um controle para escolher tema claro, escuro ou do sistema com ThemeMode. Critério de entrega: a troca funciona por teclado, mantém o resultado visível e apresenta texto legível nos três modos.
  2. Laboratório offline ampliado. Acrescente três fixtures, incluindo um endereço sem logradouro ou bairro, e permita escolher os exemplos no modo de demonstração. Critério de entrega: cada exemplo tem um teste que confere seus campos e a tela identifica claramente que são dados locais.
  3. Histórico local com limpeza. Armazene os cinco últimos CEPs consultados com sucesso, sem duplicatas, e ofereça uma ação para apagar o histórico. Critério de entrega: os itens continuam disponíveis após reiniciar o app, a limpeza funciona e existe um teste de compatibilidade para uma mudança no formato salvo.
  4. Cópia e compartilhamento completos. Inclua o complemento, quando houver, no texto copiado e implemente compartilhamento nas plataformas escolhidas. Critério de entrega: campos vazios não criam linhas desnecessárias, o conteúdo compartilhado corresponde ao endereço e o usuário recebe uma alternativa quando a ação não estiver disponível.
  5. Busca automática sem respostas antigas. Consulte após 400 ms sem digitação, somente quando houver um CEP válido, preservando a geração de cada consulta. Critério de entrega: digitação rápida não dispara consultas incompletas e um teste com respostas fora de ordem prova que o resultado antigo não substitui o novo.
